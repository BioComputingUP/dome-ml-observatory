# schema-version

Keeps `schema/` (this repo's versioned record schema + controlled vocabularies) in lockstep with
its real upstream source, `dome-triage`, without ever hand-editing a published release.

Read `schema/README.md` first if you haven't — it explains the layout, the versioning rules, and
why this folder is deliberately leaner than `BioComputingUP/dome-schema`, which it's modelled on.

## Ground rules — non-negotiable

- **Never edit a published `schema/releases/vX.Y.Z/` folder in place.** A release is immutable
  the moment it's committed. A change always means a *new* release folder.
- **Never bump `CURRENT` without a `CHANGELOG.md` entry**, and the entry must include a migration
  note — even if the note is just "additive, no action needed for existing records/consumers."
- **Never leave `CURRENT` pointing at a version that fails `validate.py`.**
- The canonical vocabulary/schema source is `dome-triage` (`mongo_landscape_export/schema/` and
  `curation_criteria/*.json`). This skill pulls *from* there; it never edits `dome-triage` itself.

## Procedure

1. **Read the current state.** `cat schema/CURRENT`, then read that release's
   `ai-ml-landscape.schema.json` and the three `vocab/*.json` files.

2. **Pull the upstream source.** Read the live versions:
   - `dome-triage/mongo_landscape_export/schema/ai_ml_landscape.schema.json` (regenerated by
     `write_schema_template.py` — if it looks stale, that script is the fix, not this skill)
   - `dome-triage/mongo_landscape_export/scripts/schema.py` (the real shape source; the schema
     JSON is a generated reference of it)
   - `dome-triage/curation_criteria/domain_vocab.json`, `modelling_branch_vocab.json`,
     `model_type_seed_vocab.json`

3. **Diff against `CURRENT`.** For the schema: any group/field added, removed, renamed, or
   retyped? For each vocab file: any term added, removed, or relabelled; any `max_tags` changed?

4. **Decide the version bump**, per `schema/README.md`'s rules:
   - Field removed/renamed/retyped, or a vocab term removed/relabelled in a way that changes what
     was previously valid → **major**.
   - Field added, or new vocab terms added (existing ones untouched) → **minor**.
   - Description-only or non-semantic vocab fixes (e.g. a typo in a label, provenance metadata
     update) → **patch**.
   - Nothing actually changed → stop here, report that, don't cut a release.

5. **Cut the new release.**
   - `mkdir -p schema/releases/vX.Y.Z/vocab`
   - Write the new `ai-ml-landscape.schema.json` — same style as the existing one: JSON Schema
     draft-07, every field with a real `description` (pulled from `dome-triage`'s field notes /
     docstrings / vocab `source`+`decided` provenance, not invented), `required` arrays kept
     accurate, `enum` used where the source has a closed vocabulary (e.g.
     `llm_classification.classification`).
   - Copy the updated `vocab/*.json` files in verbatim from `dome-triage/curation_criteria/`
     (renamed to the `domain.json` / `modelling-branch.json` / `model-type-seed.json`
     convention this folder uses).
   - Pick a real, currently-valid record for `ai-ml-landscape.example.json` — never a fabricated
     one. If the shape change is additive-only and no record yet has the new field populated with
     real data, it's fine for the example to show the new field as `null`/empty, same as the
     v1.1.0 example does for the not-yet-run enrichment fields — but never invent a plausible
     -looking value for a field nothing in the corpus actually has yet.

6. **Write the `CHANGELOG.md` entry.** Follow the v1.1.0 entry's shape: what changed, the
   migration note, and — if relevant — what's still pending (mirroring how that entry flagged the
   enrichment pass as not-yet-run without treating that as a schema change).

7. **Move `CURRENT`** to the new version, then update the hardcoded `FALLBACK_SCHEMA_VERSION` in
   `observatory-ws/src/common/schema-version.ts` to match. That file reads `schema/CURRENT` at
   module load and reports the result on `GET /api/health/ready`; the fallback only applies when
   the file can't be found at all, but it's kept in sync by hand and is easy to forget.

8. **Re-sync the UI.** `node observatory-ui/scripts/sync-schema.js` (or `npm run sync-schema
   --prefix observatory-ui`) — copies the new release's `vocab/` into
   `observatory-ui/src/assets/vocab/`. That destination is gitignored and always generated; never
   hand-edit it.

9. **Validate.** `python3 schema/validate.py schema/releases/vX.Y.Z/ai-ml-landscape.example.json`
   must pass before you consider the bump done.

10. **Report** what changed, the version bump and why, and whether any of the three places that
    mirror this shape need a matching update — this skill doesn't edit application code itself,
    it just flags what needs a follow-up:
    - `observatory-ui/src/app/core/record.model.ts` and `core/vocab.model.ts` — the frontend's
      TypeScript view of a record and of the vocabularies.
    - `observatory-ws/src/records/schemas/record.schema.ts` — the backend's Mongoose schema. It's
      deliberately minimal and `strict: false`, so an added field often needs nothing here; a
      renamed or retyped one usually does.
    - `observatory-ws/src/records/records.query.ts` — if a field that search filters on changed
      path or type, the query builder and its frontend twin (`core/search-params.ts`) both need
      the matching change. See `AGENTS.md` on why those two mirror each other.

## When there's nothing to report

If the diff in step 3 comes back empty, say so plainly and stop — don't cut an empty release or
write a changelog entry for nothing.
