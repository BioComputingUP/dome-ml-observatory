How to Use These Guidelines

These guidelines are structured around the four pillars of machine learning validation: Data, Optimization, Model, and Evaluation. Each recommendation is designed to address common pitfalls that can lead to unreliable results and a lack of reproducibility.

Pay close attention to the labels, as they distinguish between two levels of importance:

REQUIREMENT

A critical step considered essential for transparent and reproducible ML.

RECOMMENDATION

A highly advised best practice that further enhances the quality and rigor of the work.

Part 1: Data

Guiding principles for ensuring the integrity and utility of the data used for training and evaluation.

1.1 Ensure Data is Representative

The dataset's size, scope, and distribution must be representative of the biological domain and the problem being addressed. Address any significant class imbalances.

Why it matters: Using data that is too small, biased, or not representative of the real-world application can lead to models with unreliable or misleading performance.
REQUIREMENT

1.2 Guarantee Independent Datasets

The data must be partitioned into strictly independent sets for training, validation, and testing. There must be no leakage of information from the test set into the training or model selection process.

Why it matters: If the test set influences model training (even indirectly), the final performance evaluation will be over-optimistic and will not reflect how the model will perform on new, unseen data. This is one of the most critical errors in machine learning.
REQUIREMENT

1.3 Publish All Data and Splits

Whenever possible, release all datasets used for training, validation, and testing through a suitable long-term public repository. The exact data splits used must be provided.

Why it matters: Data availability is the foundation of reproducibility. It allows other researchers to verify your results, check data credibility, and accurately compare their own methods against yours.
REQUIREMENT

Part 2: Optimization

Guiding principles for the transparent and robust training of the model.

2.1 Isolate the Test Set from All Tuning

There must be a clear statement confirming that the evaluation (test) set was not used for any part of model development, including feature selection, preprocessing choices, or hyperparameter tuning.

Why it matters: Using the test set to tune parameters is a form of data leakage that leads to an over-optimistic performance report. The test set must only be used once for the final evaluation of the final model.
REQUIREMENT

2.2 Report All Hyperparameters and Protocols

Fully disclose the optimization protocol, all algorithmic hyperparameters, and the final parameters of the selected model. For neural networks, releasing training and learning curves is also advised.

Why it matters: Without these details, the results are not reproducible. Other researchers cannot understand how the model was trained or attempt to replicate the process.
REQUIREMENT

2.3 Demonstrate No Over/Underfitting

Provide evidence that the model is not overfitting to the training data or underfitting (failing to capture relevant patterns). This is typically done by comparing the error/performance on the training set versus the validation/test set.

Why it matters: An overfit model has learned noise instead of the true signal and will perform poorly on new data. An underfit model has failed to learn the signal and is not useful.
REQUIREMENT

2.4 Use Explicit Model Validation Techniques

Where appropriate, include explicit model validation techniques such as N-fold cross-validation during the model tuning phase to ensure robust hyperparameter selection.

Why it matters: Cross-validation provides a more reliable estimate of model performance and helps prevent selecting hyperparameters that are only optimal for one specific train/validation split.
RECOMMENDATION

Part 3: Model

Guiding principles for the description and dissemination of the final model.

3.1 Justify and Describe Model Choice

Clearly state the model architecture and justify the choice of model type (e.g., "black box" vs. an interpretable model). If an interpretable model is used, provide examples that demonstrate its explanatory behavior.

Why it matters: The choice of model impacts everything from performance to our ability to trust its predictions. The rationale helps others understand if the model is appropriate for the scientific question at hand.
REQUIREMENT

3.2 Ensure Model Accessibility

Provide access to the final trained model and the documented source code required to run it. Using software containers (e.g., Docker, Singularity) is highly encouraged.

Why it matters: Releasing the model and code is essential for true reproducibility and allows other researchers to apply your model to their own data or use it for comparison.
RECOMMENDATION

3.3 Report Computational Performance

Report the model's execution time (for both training and inference), ideally averaged across multiple repeats. If the model is computationally intensive, compare its performance to similar methods.

Why it matters: A model with impractical execution times may have limited real-world utility. This information is crucial for others who may want to use or build upon your work.
RECOMMENDATION

Part 4: Evaluation

Guiding principles for the fair and comprehensive assessment of model performance.

4.1 Use Appropriate Performance Measures

Select evaluation metrics that are appropriate for the specific task and data characteristics (e.g., using Precision-Recall curves for imbalanced datasets). Use community-validated measures where they exist.

Why it matters: Using inadequate metrics can hide a model's weaknesses. For example, high accuracy on an imbalanced dataset can be meaningless if the model simply ignores the minority class.
REQUIREMENT

4.2 Compare Against Meaningful Baselines

The model's performance must be compared against relevant public methods and simpler baseline models (e.g., logistic regression, a random classifier).

Why it matters: Without baselines, performance is meaningless. A complex model is only useful if it significantly outperforms simpler, established alternatives.
REQUIREMENT

4.3 Report Performance with Confidence Intervals

Provide confidence intervals or error bars for all reported performance metrics to gauge the robustness and variability of the predictions.

Why it matters: A single performance number can be misleading. Confidence intervals show the range in which the true performance likely falls, giving a much clearer picture of the model's reliability.
REQUIREMENT

4.4 Compare Methods on Identical Datasets

When comparing to related or alternative methods, the comparison should be performed on the exact same dataset and data splits to ensure a fair and direct evaluation.

Why it matters: Comparing model A on dataset X to model B on dataset Y is an invalid comparison. Fair evaluation requires a level playing field.
RECOMMENDATION
